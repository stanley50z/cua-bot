cua-bot MVP: memory, Gmail, Calendar, proactive notifications, cron

Brainstorm, 2026-10-30. Builds on the 2026-10-23 hackathon design (docs/brainstorm-2026-10-23-hackathon.html), whose code is now the baseline of this repo. Sources: Pi monorepo c7372af42 (2026-10-30), Cua fork at 99bf1ffd (SDK 0.9.0), grok-bot-0.18-reconstructed a9f633e, Google and xAI docs read today.

The short version. Keep the hackathon skeleton (one Node process, Pi Durable on SQLite, Grok 4.7 root agent, Cua Space for the screen). Add five things, in this order: a Telegram channel so the bot can reach you on your phone and you can answer it, cron routines replacing the three fixed schedule shapes, markdown memory copied in spirit from Grok Bot, Gmail over IMAP and SMTP with the app password you already have, and Google Calendar over the REST API with your own OAuth client. About 900 new lines of TypeScript on top of the existing 1,680.

The two findings that shape the design. First, Google's official Gmail and Calendar MCP servers are closed to you: they require the Workspace Developer Preview, which rejects personal @gmail.com accounts, and the Gmail server has no send tool anyway. Second, Cua's notification, routine and persistent-agent features all live in the FSL-licensed Spaces daemon and only surface inside the Spaces desktop app. Neither is a fit for a bot that has to reach you when you are away from the PC. So Google goes through plain protocols and your own OAuth client, and notifications go through Telegram plus the email path that already works.

The five features

1. Telegram: the proactive channel ~150 lines

Email already reaches you, but it is one-way and slow. Grok Bot's lesson is that a proactive bot needs a channel you carry and can answer from. Telegram is the cheapest version of that: free, mobile push, two-way, long polling so the bot needs no public URL, and a bot token is a 30-second chat with BotFather.

  • Inbound. grammy long polling. Messages from anyone except OWNER_TELEGRAM_ID are dropped. Each message becomes root.submit({type:"input", content, requestId: "tg:" + update_id, whenBusy:"followUp"}). The update_id makes redelivery after a crash a no-op.
  • Outbound. One tool, notify(text), that sends to the owner chat. The root agent learns in the persona section: a [routine] or [inbound] wake is not a chat turn, nobody is waiting, call notify only if the result is worth a phone buzz, otherwise end quietly. That sentence is lifted from Grok Bot's base prompt and is what makes routines not spam you.
  • Answer routing. When a turn came from Telegram, the final assistant text is also sent to Telegram (the current say() code already extracts it). When it came from /say, it goes back over HTTP as now.
  • Screenshots. notify accepts an optional image path, so a routine can send the Mac screenshot the computer child saved.

Cua's notify_user was the tempting shortcut. It writes to ~/.cua/persistent/notifications.json and only shows up as a toast while the Cua Spaces desktop app is running on this PC. Useful as a second surface later, not as the primary channel.

2. Cron routines ~120 lines changed

The hackathon task shape is right: a background Durable task that sleeps until the next slot, posts a [routine] turn with a stable requestId, and sleeps again. Only the schedule maths changes.

  • Grammar. 5-field cron, @hourly|@daily|@weekly|@monthly, @every 30m, optional CRON_TZ=America/Los_Angeles prefix. Same as Grok Bot, so prompts written for it carry over. Parse with croner (typed, timezone-aware, 0 dependencies). Keep accepting the old everyMinutes/dailyAt/weeklyOn objects by converting them to cron at the tool boundary, so existing routines in the SQLite file keep working.
  • Missed slots. Durable fires a passed deadline once on resume and stores only one deadline. Grok Bot and Cua's daemon behave the same way: fire once, do not replay. Keep that. Record lastFiredAt in the routines doc so the wake text can say "last ran 3 days ago".
  • Tools. schedule(title, prompt, cron), list_routines(), cancel_routine(id), plus run_routine(id) for "run it now". Cap at 50. The persona tells the model to prefer weekday daytime schedules and never bare @hourly, copied from Grok Bot's routine guidance.
  • Wake text. [routine] "Morning agenda" is due (weekdays 08:00). Nobody is waiting. Your standing instruction: ... Carry it out; notify the owner only if the outcome is worth it.

3. Memory ~200 lines

Pi Durable has no memory feature, only the primitives: documents, prompt sections, compaction. Grok Bot has a concrete, simple design that happens to fit those primitives well.

  • Storage. data/memory/profile.md and data/memory/log/YYYY-MM.md, one fact per line in Grok Bot's - (YYYY-MM-DD) fact format. Files, not a Durable doc, so you can read and edit them with any editor and the model can grep them later. A Durable session-scope doc holds only the index (fact ids, tier, date) so writes are transactional with the turn that made them.
  • Writing. Two tools: remember(fact, tier: "profile" | "log") and forget(exact text). Dedupe by sha1 of the normalised text, 500-char cap. Persona text, from Grok Bot: "Save durable facts about the owner as you learn them. Just do it and mention it in passing; don't narrate a save or ask permission."
  • Reading. A section("memory", ...) renders all profile facts plus the 30 most recent log facts within a 4,000-character budget, with a trailer "N older facts on disk; grep data/memory/log if you need them". Render from a cached string that only changes when a write happens, so the provider prompt cache is not invalidated every turn. Durable stores a positional pi.system entry only when the section text changes, which is the same freeze-between-compactions trick Grok Bot uses.
  • Long-running conversation. Keep one root conversation and let Durable's automatic compaction bound the context. Add an afterRun hook later that asks the model "anything worth remembering from this turn?" to recreate Grok Bot's extraction pass. Not in the MVP.

The Cua Volume is where Cua's own persistent agents keep memory, and it would make the files visible inside the Space. On a Windows host there is no mount and access is through the daemon's volume_* tools, so it would add a dependency on the Spaces daemon for every memory write. Local files first; mirror to the Volume as a stretch.

4. Gmail ~180 lines

Why not the official route. Google's Gmail MCP server requires Workspace Developer Preview membership, which rejects @gmail.com accounts, and its tool list (search_threads, get_thread, get_message, create_draft, label_*) has no send. The REST API with your own OAuth client works, but gmail.readonly and gmail.send are restricted scopes: in "Testing" status the refresh token dies after 7 days, and an unverified "In production" app with restricted scopes has reports of the same. A self-hosted bot that needs re-consent every week is not always-on.

So the MVP uses the protocols Google still lets a personal account use with an app password, which never expires:

  • Read. imapflow against imap.gmail.com. Tools: search_mail(query, limit) using Gmail's X-GM-RAW extension so the model writes normal Gmail search syntax (from:amazon newer_than:2d), and read_mail(uid) returning headers plus a text body capped at 8k chars. Attachments are listed by name, not downloaded.
  • Send. The existing nodemailer extension, renamed send_email, owner-only recipient unchanged. Reply-to-others is a permission-gated feature for later.
  • Stretch, and the obvious next step after the MVP. IMAP IDLE on INBOX gives a push event per new message with no Pub/Sub, no public URL and no watch renewal. Submit an [inbound] new mail from X: subject turn with requestId: "mail:" + uid and let the persona decide whether it is worth a Telegram ping. This is how "tell me when the Amazon return label arrives" works without polling.

If you later want labels, drafts or threads, switch to the REST API behind the same tool names. The gmail.readonly scope question is a Google policy risk, not a code one.

5. Google Calendar ~200 lines

Calendar has no app-password path, so this is the one place the MVP does OAuth. The scopes calendar.events and calendar.readonly are "sensitive", not "restricted". An unverified app in "In production" status with sensitive scopes shows a one-time warning screen and then issues refresh tokens that do not expire on the 7-day rule. That is the configuration to use.

  • Setup (once, your hands). GCP project, enable Calendar API, consent screen External with your address as a test user, publish to production without verification, Desktop-app OAuth client. A node src/google-login.ts runs the loopback flow with access_type=offline&prompt=consent and writes data/google-token.json. Same pattern as the existing xAI login script.
  • Tools. list_events(from, to, calendar?), create_event(title, start, end, description?, attendees?), update_event(id, patch), free_busy(from, to). Dates are ISO strings in the owner's timezone, which the persona states once. Use googleapis, or plain fetch against Calendar v3 if the 15 MB dependency bothers you; the surface is four endpoints.
  • Proactive use. The first routine to ship is the one that makes the whole thing feel like Grok Bot: weekdays 07:30, list_events for today plus unread mail from the last 12 hours, one Telegram message.

Not chosen: Google's Calendar MCP (same preview gate as Gmail, and you would still need the agentic OAuth client), CalDAV (OAuth anyway, worse API), the private ICS URL (read-only, polled, no create).

Decisions you need to make

  1. Telegram as the primary channel. Alternatives are Discord DM (similar effort), iMessage via the Mac mini (fragile), or email only (slow, one-way). I recommend Telegram.
  2. Gmail account. The IMAP/SMTP path uses the same app password as today. If you would rather have labels and drafts from day one, say so and the Gmail extension becomes REST with the 7-day re-consent risk.
  3. Main model. The code still defaults to Grok 4.7 via your SuperGrok login. Pi supports Anthropic and others with a one-line change if you want the bot itself on a different model.
  4. The old folder. ~/grokbot-hackathon is now fully represented here except its .env, 20 MB of runtime data and 335 MB of node_modules. Copy the .env over, then delete it when you are ready; I have not touched it.
