Self-hosted Grok bot on Pi Durable + Cua Spaces

Hackathon brainstorm, 2026-10-23. Opus 5.5 led and wrote the design. Four Grok subagents did the research and the adversarial review (three on Pi xai/grok-4.7, one on Grok Build grok-4.7). Sources: Pi monorepo 136b87e8a, Cua ac7a1674, grok-bot-0.18-reconstructed (HEAD, shallow clone).

The short version. One Node 22 process, about 400 lines of new TypeScript. It opens a Pi Durable Harness on SQLite and runs a Grok 4.7 main agent with four small extensions: computer, email, routines, pr. Computer use and coding each run as a Grok child conversation, copied from Durable's subagent examples. Cua supplies the desktop (your paired Mac mini) and, surprisingly, the routine clock. Everything else is glue.

The pitch writes itself because Durable is genuinely good at one thing judges can see. You kill -9 the bot on stage, start it again, and the scheduled job still fires on time.

Your Gmail MCP question

Pi Durable can connect to MCP servers. The official Gmail MCP can't send mail. Use plain SMTP.

Durable has no MCP config of its own, but the sibling package @earendil-works/pi-mcp is a standalone client with stdio, Streamable HTTP and OAuth (PKCE, dynamic registration, refresh). Its README already shows the ~20-line loop that wraps every MCP tool as an agent tool (packages/mcp/README.md:34-54). The Durable version is the same loop with defineTool and Type.Unsafe(tool.inputSchema). So the transport is not the blocker.

Gmail is the blocker. Google's hosted server at https://gmailmcp.googleapis.com/mcp/v1 is a Developer Preview: you need Workspace Developer Preview enrollment, a GCP project with two APIs enabled, and a Web OAuth client. Its only write tool is create_draft. There is no send tool, and the scopes stop at gmail.compose. (Google: Configure the Gmail MCP server.) Community servers such as flujo-app/mcp-gmail-oauth can send, but they call themselves early and you would be self-hosting a second service.

For the MVP, use nodemailer over Gmail SMTP with an app password. That's one dependency, about 30 lines, and no OAuth dance during a demo. Gmail MCP read tools via pi-mcp go on the stretch list.

Architecture

Inbound

  • POST 127.0.0.1:<port>/say (node:http, ~15 lines)
  • say.py "text" as the CLI that posts to it
  • Routine wake-ups, internal

Why HTTP and not just a CLI: Durable allows one process per storage file with no cross-process lock (durable/README.md:783), so a second process can't open the SQLite file to submit.

Outside world

  • Cua Space: Mac mini via @trycua/cua embedded().spaces(), reading ~/.cua/spaces.json
  • Gmail SMTP
  • GitHub via gh (already installed and authed on this PC)
  • api.x.ai (XAI_API_KEY)

The grok-bot reconstruction is where the shape comes from. Its main agent never clicks. GUI work goes to one computerUse subagent at a time because they share one screen. Repo work goes to a coding agent that runs gh pr create, and routines arrive as [routine] turns. Those rules are good, and we keep them. The reconstruction's code we leave alone (see licensing below).

The four extensions

computer

The main agent sees one tool, computer_use(task). It creates a child conversation (example 21) whose tool list is only the driver tools from the Space: screenshot, click, type_text, launch_app, get_window_state, plus space_bash. The child model is grok-4.7, which takes image input. The child does the looking and clicking, then returns a text summary and the path of its last screenshot.

We use the driver tools rather than spacesd().click(x, y) on purpose. The raw spacesd click takes screen points, while screenshots come back in pixels, downscaled, with no origin. The CLI does origin + pixel / scale to bridge them (libs/cua/crates/cua-cli/src/mcp.rs:822-834). The driver tools already accept screenshot pixels, so the bridge needs no coordinate math at all.

const space = await embedded().spaces().space(process.env.CUA_SPACE_ID!) // must already be in ~/.cua/spaces.json
const driverTools = (await space.listTools()).map((t) => defineTool({
  name: t.name,
  description: t.description ?? t.name,
  parameters: Type.Unsafe({ ...t.inputSchema, type: "object", properties: t.inputSchema.properties ?? {} }),
  execute: async (args) => ({ output: toLlmContent(JSON.parse((await space.callTool(t.name, args)).contentJson)) }),
}))

To check on day one: the exact listTools / callTool signatures (cua_sdk.ts:28829-28879), and whether contentJson parses as an MCP CallToolResult. Pass a max dimension of about 1200 px on screenshots. Durable doesn't resize tool images, and xAI isn't in pi-ai's image-size table.

email

send_email(subject, body, attachments?). The recipient is fixed to OWNER_EMAIL, so the model can't mail anyone else. Attachments are file paths, typically the screenshot the computer child saved. The model never has to pass image bytes. Leave replay at its default "unsafe". If the process dies mid-send, the model gets an "interrupted" result and decides what to do, which beats a silent double-send.

routines

schedule(title, prompt, schedule) takes a Cua RoutineSchedule (everyMinutes, dailyAt, weeklyOn) and starts a background Durable task with two phases:

wait: (task, rt, cx) => {
  const due = nextFireDate(task.input.schedule, new Date()).getTime()   // use the Harness clock in real code
  return rt.sleepUntil(due, { phase: "fire", due }, cx)
}
fire: async (task, rt, cx) => {
  const due = task.state.checkpoint.due
  await root.submit({ type: "input", content: routineTurnText(task.input), requestId: `${task.id}:${due}` }, cx)
  return rt.commit(() => ({ status: "running", checkpoint: { phase: "wait" } }), cx)
}

Three details matter here. The review caught all three, and I checked them against source.

  • Create the task with background: true and return from the tool right away. If the schedule tool awaited a task that submits to the same root conversation, the run could never finish. The submit is queued behind it as a follow-up (durable/src/harness/submissions.ts:240-257).
  • The requestId has to be stable per firing. A phase reruns from the top after a crash. Without a stable ID, a crash between submit and commit fires the routine twice. With one, Durable returns the existing submission.
  • This is the code behind the restart demo. A sleeping task holds no invocation and survives the restart. Its timer also keeps Node alive.

pr

open_pr(repo, instructions) is the same foreground-child helper. This time the child has CodingTools, a Node env whose cwd is a fresh clone under data/work/<id>, and instructions to finish with gh pr create and print the URL. It returns the URL, and the main agent emails it. On Windows the built-in bash runs Git Bash (durable/src/env/node.ts:233-256), which gh and git handle fine.

A beforeTool hook blocks any git push or gh call whose target isn't in ALLOWED_REPOS. Be honest in the pitch that this is a string check on the bash command, a demo guardrail rather than a sandbox. To actually isolate the PR work, run the child's shell on the Space with space_bash instead of on the host. It's a good stretch goal and a nice Cua talking point.

During the build, I'd keep the split this session used. I (Opus) own the skeleton, the shared subagent helper, integration and the final review. Grok Build agents do the volume work:

  1. Four Grok Build implementers in parallel worktrees, one per extension. Each writes its extension plus a test on Durable's faux provider, the way the examples do.
  2. One Grok Build adversarial reviewer per merged extension. This session's single review caught five real bugs.
  3. One Grok Build agent that rehearses the demo end to end and reports timing.

That's roughly 8 to 10 Grok runs against 1 Opus thread, which is a fair "decent amount" for an xAI-sponsored event, and each Grok run has a clear job.

Risks the review found

A Grok Build reviewer attacked the first draft of this design. I checked each finding against source and kept the ones that held up. All of them are already fixed in the sections above.

SeverityIssueFix
highKilling the bot mid-tool does not resume the tool. Default replay: "unsafe" writes an "interrupted" result and aborts owned children (durable/src/harness/tool.ts:181-197, verified).Script the kill for while the routine is asleep. That's the case Durable makes bulletproof.
highA schedule tool that waits on its own routine deadlocks the turn.background: true, return immediately.
highPixel-to-point click math with the raw spacesd API is easy to get wrong.Use the driver tools, which take screenshot pixels.
highChild conversations inherit every parent tool. CodingTools fail with "No execution environment is configured" unless Harness.open gets an env.configure({ tools }) per child. Pass a Node env, with the clone as the PR child's cwd.
medDurable doesn't resize screenshots. The model can't put image bytes into an email.Cap screenshots at ~1200 px. Save PNGs to disk and attach by path.
medspace("direct:…") only opens a Space already in the registry. The Windows build needs the @trycua/cua-win32-x64-msvc optional dep.Your Mac mini is already registered in ~/.cua/spaces.json. Check npm installs the win32 binary (it's published at 0.7.0).
lowNode SQLite needs nothing special.Node ≥ 22.19. WAL and busy timeout are set for you.

The 3-minute demo

  1. 0:00. The bot is already running. Say: "Every minute, look at the Notes app on my Mac and email me its first line with a screenshot." The bot creates the routine and confirms by email.
  2. 0:40. Show the Mac mini screen as the computer child opens Notes and takes a screenshot. The first email arrives with the PNG attached.
  3. 1:20. kill -9 the bot while the routine sleeps. Wait. Start it with start.py. The stored deadline rearms the timer, and the next email arrives on schedule. This is the Durable moment, so take your time with it.
  4. 2:10. "Fix the typo in the README of <demo repo>." The coding child clones, edits and runs gh pr create, and the PR link lands in the inbox.
  5. 2:50. Close with one slide: ~400 lines of glue, one process, self-hosted, Grok all the way down.

Pre-seed the Notes content, gh auth, the demo repo with a planted typo, and the Space pairing. Leave Calendar out, because permission prompts on stage are a coin flip.
